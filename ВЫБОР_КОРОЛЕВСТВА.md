## 2. Главный вывод
- **Королевство выбирается только на клиенте.** Отдельной команды «выбрать королевство / создать персонажа» нет. Сервер узнаёт королевство из поля `kingdom_id` в **первом `init`** после `new_account`. Имени персонажа нет (name=Lord по умолчанию).
- getServersState — только чтение (открыто/закрыто), в создании не участвует.
- Новый персонаж = **новый passport-аккаунт** (новый fpid, guid, auth_token), не «второй замок» фермы. Ферма не связана с ним на сервере (bind не делался, social_infos у нового пусто).

## 3. Что меняется / постоянно
Постоянно: device_id, android_id, fp_device_id, origin_guid, anon_id, gaid, app_id, game_id, pkg_channel, версии.
Меняется: guid (новый на каждый new_account), fpid, auth_token/session_key, ak, uid, gateway_name/finger_print, game_token, chat_token.
init.kingdom_id: при создании = выбранное королевство; при обычном перелогине 0 или последнее.

## 4. Чего не можем расшифровать
Два запроса fp-passport без `method` (тело/ответ — base64-шифр, начало `7ciSPt6a...` / `4dOKPUYi...`) перед каждым **social_login** (возврат на ферму). Для new_account они НЕ нужны: new_account — обычный form-запрос без шифра.
Также social_login использует access_token "FP|..." аккаунта KG фермы — его трогать нельзя.

## 5. Можно ли через inject
- new_account+init — это смена сессии, а не команда в текущей сессии; 13_inject_cmd/inject.py шлют команды внутри живой сессии клиента → **напрямую нельзя**.
- Вариант А (рекомендую, без риска для фермы): пользователь/ADB-тапы жмут «новый персонаж» в ЛЮБОМ открытом королевстве, а inject.py переписывает `kingdom_id` в первом `init` после new_account на целевое (с проверкой: state==1 по getServersState, fpid != 182070973). Не проверено, примет ли сервер — гипотеза.
- Вариант Б: ADB-тапы по UI выбора (листание страниц до нужного диапазона) — надёжно, но хрупко к разметке.
- Вариант В: свой скрипт (не 12_login.py) passport new_account + versionDiff2 + init — тогда клиент в эмуляторе не будет в этой сессии, план через inject не пойдёт. Не рекомендую.
- Риск для фермы: сам new_account ферму не трогает. Риск — возврат на ферму (social_login + шифрованные вызовы) и любые init с fpid 182070973 из наших скриптов. Правило: скрипты никогда не шлют init/social_login с fpid фермы; возврат на ферму — только руками.
- Весь трафик — только через Surfshark (203.0.113.20).

## 9. Углублённый разбор (31.10, 17:3x)
**new_account — НЕ шифрован.** Обычный urlencoded POST на gog-passport.kingsgroupgames.com/client_api.php, подпись `Authorization: FP 2064:` HMAC-SHA256 (FunplusGameKey) — та же, что у token_login. Проверено `passport_sign()` из 12_login.py на всех 4 захватах (3 в flows_3rounds + 1 в flows_inject5): **совпадение 4/4**.
Поля по порядку: method=new_account, app_version, device_id, session_id(пусто), device_level, l, pkg_channel, origin_guid, sdk_version, fp_device_id, imei, guid(новый случайный 32 hex), android_id, app_id, game_id. Нет auth_token. Заголовок Fp-Device-Token (с устройства, как у token_login).
Ответ: fpid, is_new=true, auth_token (= session_key для init).

**Первый init после new_account:** AES-ECB(ak) JSON, без подписи и без HMAC; отличия от обычного init — `kingdom_id`=выбранное и `is_old_account: 1`. Поле gateway_connid в HTTP-ответах не встречается (видимо от игрового шлюза; 12_login.py берёт его из device-профиля).
=> **Номер королевства просто пишется в init.kingdom_id.** Подменить его в inject.py технически можно (расшифровать ak → поменять → зашифровать), подписи нет.

**Зашифрованные вызовы** (7ciSPt6a… / 4dOKPUYi…): `fp-passport.funplus.com/api/session_login` и `/rolesapi/get_dw_bind_list` (text/plain, шифр SDK). Идут ТОЛЬКО перед social_login при возврате на ферму. **Для создания замка не нужны.** Расшифровка (dex/jadx) не делалась.

**Возврат на ферму:** social_login (kg-токен фермы "FP|…") — скриптом не делаем: это токен фермы и риск для 71206420. Ферма остаётся залогиненной в своём окне; на netbot_test возврат — руками.
