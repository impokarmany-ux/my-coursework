# Слой 2: шифрование тела HTTP API (поверх TLS)

Учебная заметка. Читай сверху вниз. Цель — понять, **почему после успешного MITM
мы всё ещё видим «кашу»**, и как искать ключ.

---

## 1. Два замка на одной двери

Представь посылку:

1. **Внешний замок (TLS)** — курьер (интернет) не читает письмо. Мы его сняли
   через mitmproxy: сертификат принят, pinning нет. В `flows.mitm` видны URL,
   заголовки и «тело» запроса.
2. **Внутренний замок (AES в приложении)** — само письмо ещё раз зашифровано
   игрой **до** отправки. Поэтому `Content-Type: application/octet-stream`,
   а не читаемый JSON.

Passport (`gog-passport.../client_api.php`) и первые «прогревочные» вызовы
(`versionDiff2`, `manifest`) идут **обычным JSON**. Как только сервер включил
шифрование (`"en": true` в manifest) — дальше почти всё `/api/` бинарное.
Заголовок `GDataVer: v1` стоит и на JSON, и на octet-stream (у нас 126 таких
запросов к `gog-global.../api/`).

> Важно для обучения: «я расшифровал TLS» ≠ «я читаю игровой протокол».
> Второй слой — отдельная задача reverse engineering кода, не сети.

---

## 2. Что видно глазами в сырых телах

Папка: `mitm\raw_bodies\` (файлы `NNN_req.bin` / `NNN_resp.bin`).

Наблюдения (проверь сам скриптом `07_decrypt_api.py`):

| Признак | Что значит |
|--------|------------|
| Длина кратна **16** | Размер блока AES (128 бит) |
| Энтропия ≈ 7.5–8.0 | Похоже на нормальный шифр, не простой XOR |
| Много ответов с **одинаковым** первым блоком `62 40 66 5a …` | Один и тот же начало plaintext (часто `{"payload":…}`) + фиксированный IV **или** ECB |
| Внутри большого ответа некоторые 16-байтовые блоки повторяются | Слабый намёк на ECB (в CBC такое реже) |
| Сервер пишет `Content-Type: application/json`, а тело — бинарное | Сервер «врёт» типом: после расшифровки там JSON |

Первые два запроса в сессии ещё JSON — это bootstrap. Остальное — шифр.

## 3. Цепочка в коде игры (из `dump.cs`)

Имена важнее RVA: в файле **несколько** склеенных дампов. Ищи по имени класса.

Упрощённо, от кнопки в UI до провода:

```
UI / менеджер фичи
    → Utils.SendRequest(porttype, Hashtable, …)
        → RequestManager (собирает LoaderInfo / LoaderHttp)
            → сериализация Hashtable → JSON-строка (ещё plaintext в памяти)
            → Encryptor[WithRandomKey].NeedEncrypt(info)?
                  да → LoaderEncode(info)  → byte[]
            → UnityWebRequest / libcurl
                  Content-Type: application/octet-stream
                  заголовок GDataVer: v1
                  тело = зашифрованные байты
```

Ключевые классы в пространстве **Funplus.AesKeyCoder** (и рядом):

| Класс | Роль |
|-------|------|
| `Encryptor` | Статический путь: `Open(string key)`, `LoaderEncode` / `LoaderDecode` |
| `EncryptorWithRandomKey` | Боевой путь: `Open(string ak, long ai)`, хранит `_ak` / `_ai` |
| `AesCoder` | `Initialize()` без параметров, `Encode(string)→byte[]`, `Decode` |
| `AesCoderWithRandomKey` | `Initialize(string ak, long ai)`, дальше Encode/Decode |
| `AesKeyCoderMethod1`…`5` | Варианты `Encrypt/Decrypt(data, key="KOA")` — похоже на **деривацию/обёртку ключа**, default `"KOA"` |
| `AesMethodReflectionFactory` | Выбор Method1–5 (скорее по `ai`) |
| `AesDebugUtils` | `FileFolder = "/aes_key"` — **папка на устройстве**, Save/Load `(ai, ak)` для отладки |
| `BaseLoaderInfo.ForceEncrypt` | Принудительно шифровать даже если флаг сессии ещё не подняли |
| `IsRandomKeyAesOn` | Переключатель: random-key путь или обычный Encryptor |

Логи в строках игры подтверждают путь:

- `"[System]EncryptorWithRandomKey Open."` / `Close.`
- `"[Encryptor]Aes Create Fail."`
- `"application/octet-stream"`, `"GDataVer"`, `"Funplus.AesKeyCoder"`

Ответ сервера идёт обратно через `LoaderDecode` → снова JSON в Hashtable.

**Watcher** (TCP 17681) — **другой** канал (пуш с сервера), со своим `Cipher`.
Его мы здесь не разбираем; HTTP API — отдельная ветка.

## 4. Откуда ключ? (честно: пока не поймали)

Кандидаты, которые мы **проверили и отвергли / не подтвердили**:

1. **Passport `token_login`** — открытый JSON, полей `ak`/`ai` нет.
2. **Manifest** — есть `"en": true` (шифрование включено) и чужие
   `api_key` / `api_iv` для FunPlus account URL. Это **не** игровой AES-ключ
   (и наивный AES с `api_iv` тело не открыл).
3. **Строка `"KOA"`** — default у Method1–5. Наивный AES-ECB/CBC с
   `KOA` / `md5(KOA)` / padding до 16 байт на сохранённых телах — **не дал JSON**.
4. **Папка `/aes_key` на устройстве** — у `com.diandian.gog` на тестовом окне
   **пуста**. В release `Open(..., noSave=true)` или Save просто не вызывается.
   Ключ живёт в **статических полях** `_ak` / `_ai` в памяти процесса.

Рабочая гипотеза (ещё не доказана дампом памяти):

> После bootstrap сервер (или один из первых уже-шифрованных ответов / отдельный
> login к game API) отдаёт пару `(ak, ai)`. Клиент вызывает
> `EncryptorWithRandomKey.Open(ak, ai)` → `AesCoderWithRandomKey.Initialize` →
> дальше все `LoaderEncode`/`Decode` идут этим AES.

Точный режим (ECB vs CBC, где IV, PKCS7 или нет) сидит внутри
`AesCoder*.Initialize` / `Encode` в нативном коде `libil2cpp.so` — в C# дампе
только сигнатуры.

## 6. Следующий конкретный шаг (выбери один)

### A. Frida на тестовом окне (быстрее для ключа)

Игра на LDPlayer идёт как **ARM64 через libnb** — обычный хук x86-Frida на
Managed методы IL2CPP **раньше не цеплялся**. Варианты:

1. Frida **gadget / arm translator-aware** хук, либо эмулятор без трансляции.
2. Хукать не C#, а **экспорт/символ** после того, как Ghidra покажет
   native-обёртку Encode (сложнее).
3. Проще по смыслу: патч/лог вокруг `Open` если найдём вызов в smali/native —
   но для Il2Cpp чаще идут в Ghidra.

Практичный план на тест-окне: поднять Frida, попробовать
`Java`/`Module` найти `libil2cpp.so`, поставить interceptor на RVA
`AesCoderWithRandomKey.Initialize` / `EncryptorWithRandomKey.Open`
(RVA из dump.cs **того** куска, где TypeDefIndex ~72325 — сверь имя!).
На входе дампануть `ak` (string) и `ai` (int64). Один удачный логин —
ключ в кармане, `07` дописывается до настоящего decrypt.

### B. Ghidra (медленнее, но учит «настоящему» RE)

1. Открыть `libil2cpp.so` (arm64) из APK.
2. Перейти на VA/offset `AesCoderWithRandomKey.Initialize` /
   `AesCoder.Encode` (из dump.cs).
3. Найти: `Aes.Create` / `CreateEncryptor`, Mode, IV, как из `(ak,ai)`
   собирается 16/32-байтовый ключ (через Method1–5?).
4. Записать алгоритм в `07_decrypt_api.py` и проверить на `raw_bodies`.

### C. Не делать

- Не гонять Frida/MITM на фермах.
- Не светить `ak`/токены в чат и в git — в заметках редактировать.

## 7. Мини-словарь

- **TLS / MITM** — снимаем транспортное шифрование.
- **AES** — блочный шифр; длина тела кратна 16 — хороший намёк.
- **ECB / CBC** — режимы AES; ECB одинаковые блоки plaintext → одинаковый
  ciphertext (плохо для безопасности, удобно для RE).
- **Pinning** — проверка «своего» сертификата; у GoG на этом билде **нет**.
- **Il2Cpp dump.cs** — «телефонный справочник» методов без тел; тела — в `.so`.
- **ak / ai** — session key material для `EncryptorWithRandomKey`.

> TLS мы победили; игровые `/api/` после bootstrap закрыты **AES из
> Funplus.AesKeyCoder** (`EncryptorWithRandomKey` + `AesCoderWithRandomKey`).

> алгоритм в Ghidra. Ни одно тело из `raw_bodies` пока **не расшифровано**.
