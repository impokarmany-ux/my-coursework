# Что связывает новые аккаунты между собой и с фермой

Только офлайн-анализ. В сеть игры ничего не отправлялось. Игру, ферму и inject не трогали.
uid, fpid, IP и токены в тексте не приводятся.

## Главный вывод
Сейчас `15_new_account.py` берёт готовый профиль устройства (`--device`, например `mitm\device_profile_*.json`) и **заново генерирует только `guid`**. Все остальные идентификаторы (`device_id`, `android_id`, `fp_device_id`, `origin_guid`, `Fp-Device-Token`) берутся из одного профиля и, значит, **одинаковы у всех «новых» аккаунтов и совпадают с фермовым устройством**. Для «заныкаться» это главная дыра: сервер по любому из них видит, что это одно устройство. Чтобы замки были несвязанными, нужен отдельный набор идентификаторов на каждый замок.

## По каждому идентификатору

### Fp-Device-Token (заголовок HTTP, FunPlus SDK)
- **Откуда:** выдаётся сервисом FunPlus (device/service) при первой регистрации устройства; в наших запусках берётся готовым из профиля.
- **Свой на замок:** да, но его нельзя просто сгенерировать локально — это серверный токен устройства. Нужно пройти регистрацию устройства в FunPlus (fp device service) со свежими `device_id`/`android_id` и получить новый токен. Это сетевой вызов, т.е. задача на будущий клиент, а не локальная подделка.
- **Риск при несовпадении:** высокий. Если токен не соответствует устройству/отпечатку, FunPlus может отклонить или пометить сессию. Переиспользование одного токена на многих аккаунтах — прямая связка.

### device_id (32 hex)
- **Откуда:** идентификатор установки, генерируется клиентом (случайные 16 байт → hex). В профиле это строка вида `9e0b…`.
- **Свой на замок:** да, легко — `uuid.uuid4().hex`. Серверной подписи нет, это просто строка, которую сервер запоминает.
- **Риск:** низкий сам по себе, но если оставить общий — это явная связка. Менять обязательно.

### android_id (16 hex)
- **Откуда:** Settings.Secure.ANDROID_ID устройства/эмулятора (`dbd5…`).
- **Свой на замок:** да — 8 случайных байт → hex. Проверки подписи нет.
- **Риск:** низкий. Но несколько аккаунтов с одним android_id — связка. На настоящем устройстве он один на профиль ОС, так что «много разных android_id с одного IP» тоже выглядит ненатурально — см. раздел про IP ниже.

### fp_device_id (длинный hex с префиксом-временем)
- **Откуда:** FunPlus device id. Важно: начинается с временной метки (`202610150512…`), дальше — хэш от характеристик устройства. То есть формат = `yyyymmddHHMM` + hex.
- **Свой на замок:** частично. Формат воспроизводим (текущее время + случайный/хэш-хвост), но «правильный» id выдаёт SDK вместе с Fp-Device-Token. Лучше получать его тем же вызовом регистрации устройства, что и токен, чтобы они были согласованы.
- **Риск:** средний/высокий. Если `fp_device_id` и `Fp-Device-Token` рассинхронизированы, сервер FunPlus это заметит.

### origin_guid (32 hex)
- **Откуда:** первичный guid установки FunPlus (`fb66…`), создаётся один раз при первой установке и дальше не меняется.
- **Свой на замок:** да — `uuid4().hex`. Подписи нет.
- **Риск:** средний. Это «первый guid устройства»; один и тот же origin_guid у многих аккаунтов — сильный признак одного устройства. Менять.

### guid (32 hex)
- **Откуда:** текущий guid сессии; `15_new_account.py` уже генерирует новый на каждый запуск (`uuid4().hex`).
- **Свой на замок:** да, уже делается.
- **Риск:** низкий, уже разный.

### gaid (Google Advertising ID, UUID)
- **Откуда:** рекламный id Google Play Services. В init сейчас передаётся пустым/из профиля.
- **Свой на замок:** да — формат обычного UUID (`uuid4()` со стандартными дефисами). Серверной подписи нет.
- **Риск:** низкий для логина, но важен для antifraud/атрибуции. Пустой gaid в неудачном init (ok=3) был одним из отличий. Лучше ставить правдоподобный UUID, разный на замок.

### appsflyer_id (цифры-цифры: timestamp-random)
- **Откуда:** AppsFlyer SDK, формат `<ms_timestamp>-<random>`.
- **Свой на замок:** да — текущее время в мс + случайное 19-значное число, формат легко повторить.
- **Риск:** низкий. Общий id на всех — связка в атрибуции. Делать разный.

### push device_token (FCM)
- **Откуда:** токен Firebase Cloud Messaging, выдаётся Google при регистрации пуш-канала. В наших запусках пуст (`device_token: ""`).
- **Свой на замок:** нет, локально не сгенерировать — это токен Google. Можно оставлять пустым (в init он уже пустой и это проходило). Настоящий нужен только чтобы реально получать пуши.
- **Риск:** низкий, если пустой у всех одинаково. Чужой/фермовый push-токен подставлять нельзя — свяжет каналы.

### anon_id (вид "XZ"+uuid)
- **Откуда:** клиентский анонимный id, `12_login.py` генерирует `"XZ" + uuid4()` если нет в профиле.
- **Свой на замок:** да, уже так и делается.
- **Риск:** низкий.

### gateway_* (gateway_name, gateway_finger_print, gateway_connid)
- **Откуда:** приходят от TCP-шлюза в приветствии (см. ШЛЮЗ.md). Анонимны, свежие на каждое подключение.
- **Свой на замок:** да — каждое новое подключение к шлюзу даёт свой набор. Подделать без подключения нельзя (ConnID — счётчик, Fingerprint — случайный 64-битный).
- **Риск:** если подставить чужие (фермовые) живые поля — можно привязать пуш-канал фермы к новому аккаунту (это и видели: init прошёл с фермовыми полями). Нужен свой шлюз на каждый замок.

## Подпись запросов
`Authorization = "FP 2064:" + base64(hex(HMAC-SHA256(FunplusGameKey, тело)))`. Ключ общий для приложения, не на устройство. То есть подпись не привязывает к устройству — привязка идёт через сами идентификаторы в теле. Порядок полей в теле важен (сверяется с захваченными new_account).

## Что ещё связывает, помимо идентификаторов
- **IP.** Все аккаунты сейчас выходят через один прокси (18081 → Surfshark). Один IP на множество «разных устройств» — сильнейшая связка, сильнее большинства id. Для «заныкаться» нужны разные выходные IP на замки или хотя бы разнесение по времени.
- **User-Agent / модель устройства.** В профиле зашит один UA (SM-G975N, Android 9). Много аккаунтов с идентичным UA — признак. Желательно варьировать модель/версию.
- **Тайминги и поведение.** Одинаковые задержки и последовательность команд тоже коррелируют.

## Рекомендация для несвязанных замков
1. На каждый замок генерировать свежие: `device_id`, `android_id`, `origin_guid`, `guid`, `gaid`, `appsflyer_id`, `anon_id` (все локально).
2. `fp_device_id` + `Fp-Device-Token` получать согласованно через регистрацию устройства FunPlus (сетевой шаг, через прокси).
3. `gateway_*` — со своего подключения к шлюзу (см. ШЛЮЗ.md), не брать чужие.
4. push device_token оставлять пустым либо свой (не чужой).
5. Разнести выходные IP, варьировать UA/модель, не делать запуски залпом.
