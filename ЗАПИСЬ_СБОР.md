# Безопасная запись: сбор наград города

Учебная заметка по разбору **одной write-команды** из полного круга.
Цель — понять параметры, сравнить образцы и (осторожно) послать её сами.

Дата разбора: 31 октября 2026 (Europe/Sofia).
Окно: только `netbot_test`. Фермы ботом не трогаем.

---

## 1. Какую команду нашли

В полном круге **нет** отдельной команды «тапнуть ферму/мельницу и забрать ресурс».
Клиент, похоже, либо копит ресурсы локально и синкает иначе, либо мы просто
не нажали обычный сбор с построек во время записи.

Зато есть явный **сбор наград** туториала нового замка:

| Поле | Значение |
|------|----------|
| Обёртка | `class=call` / `method=commit` |
| Операция | `params.op = "Prophase:collectCityAllRewards"` |
| Смысл | Забрать все накопленные награды выбранного типа (у нас — с руин) |
| Аккаунт в образцах | новый замок `uid=98565609` (не старая ферма) |

Рядом по сценарию всегда идёт:

1. `Prophase:clearCityRuin` — расчистить руину (`args.ruin_id`) → в `user_data` появляются награды.
2. `Prophase:collectCityAllRewards` — забрать эти награды → растут `food`/`wood` в `user_city.resource`.

`clearCityRuin` **не** считаем «безопасным сбором»: она меняет карту города.
Для первого write берём только `collectCityAllRewards`.

Файлы образцов (расшифровка):

- `mitm/decrypted/1247_req.json.txt` + `1247_resp.json.txt`
- `mitm/decrypted/1459_*`
- `mitm/decrypted/1559_*`
- сводка без секретов: `mitm/write_samples/collect_compare.json`
- полный запрос (с токенами, только локально): `mitm/write_samples/collectCityAllRewards_1247_full.json`

## 2. Формат запроса (схема)

Клиент шлёт **не** короткий `Mail:getUnReadCount`, а обёртку `call:commit`:

```json
{
  "race_mode": 0,
  "seq": 83,
  "class": "call",
  "method": "commit",
  "req_id": "1793441718803.15",
  "params": {
    "os": "android",
    "op": "Prophase:collectCityAllRewards",
    "cv": "1793346785632",
    "token": "<JWT>",
    "client_version": "14.2.0",
    "bvr": "14.2.0.8514.09291114.R",
    "bvg": "9f839b1",
    "fpid": "26426239169882",
    "session_key": "<SESSION>",
    "args": {
      "type": "ruin",
      "uid": 98565609
    }
  }
}
```

Потом JSON → AES-128-ECB + PKCS7 → `POST /api/` с заголовком `GDataVer: v1`
(см. `ОТПРАВКА.md` и `10_send_cmd.py`).

### Обязательные поля

| Поле | Где | Зачем |
|------|-----|--------|
| `class` / `method` | корень | всегда `call` / `commit` для таких действий |
| `params.op` | params | имя операции `Prophase:collectCityAllRewards` |
| `params.token` | params | JWT сессии (в нём `uid`, `fpid`) |
| `params.session_key` | params | ключ сессии после `call:init` |
| `params.args.type` | args | тип источника наград; в круге всегда `"ruin"` |
| `params.args.uid` | args | чей город; **должен совпадать** с `uid` в JWT |
| `params.fpid` | params | FunPlus id аккаунта (строка) |
| `params.client_version` | params | `"14.2.0"` |
| `req_id` | корень | уникальный id запроса (`unix_ms.xx`) |
| `seq` | корень | номер commit в сессии; неверный → `ok:98` и подсказка next |

### Поля, которые в круге не менялись (почти константы клиента)

| Поле | Значение в круге | Комментарий |
|------|------------------|-------------|
| `race_mode` | `0` | режим гонки/ивента; у нас 0 |
| `os` | `"android"` | платформа |
| `cv` | `"1793346785632"` | одно и то же на весь круг |
| `bvr` | `"14.2.0.8514.09291114.R"` | точная сборка |
| `bvg` | `"9f839b1"` | git/hash сборки |

### Что меняется между вызовами

| Поле | Образец 1 | Образец 2 | Образец 3 |
|------|-----------|-----------|-----------|
| файл | 1247 | 1459 | 1559 |
| `seq` | 83 | 202 | 260 |
| `req_id` | …718803.15 | …811479.44 | …858423.97 |
| `args` | `{type:ruin, uid:98565609}` | то же | то же |
| id руины в ответе | `156000017` | `156000019` | `156000010` |

Вывод для обучения: **в запрос id руины не передаём** — сервер сам
забирает все готовые награды типа `ruin` для этого `uid`.
Меняются только `seq` / `req_id` (и секреты сессии).

## 3. Формат ответа

Успех: `"ok": 1`.

```json
{
  "ok": 1,
  "time": 1793441718383,
  "payload": {
    "rewards": {
      "156000017": {
        "1": {"food": 1200},
        "2": {"food": 1200},
        "3": {"wood": 1500},
        "4": {"wood": 1500}
      }
    }
  },
  "data": {
    "set": {
      "user_data": [
        {
          "uid": 98565609,
          "id": 48,
          "content": {
            "ruin": {
              "156000017": []
            }
          }
        }
      ],
      "user_city": [
        {
          "uid": 98565609,
          "city_id": 98565609,
          "resource": {
            "resource": {
              "wood": 4110,
              "food": 3510,
              "ore": 1000,
              "silver": 1000
            },
            "update_time": 1793441718
          }
        }
      ]
    }
  }
}
```

Как читать:

- `payload.rewards` — что только что забрали (по id руины → слоты → ресурс).
- `data.set.user_data[].content.ruin[id] = []` — руина «опустошена» после сбора.
- `data.set.user_city[].resource.resource` — **новые** запасы города. Это главный
  признак, что запись сработала: food/wood выросли.

Сравнение трёх ответов (запасы после сбора):

| # | food | wood | ore | silver | сумма food+wood в rewards |
|---|------|------|-----|--------|---------------------------|
| 1 | 3510 | 4110 | 1000 | 1000 | 1200+1200+1500+1500 = 5400 |
| 2 | 5910 | 7110 | 1000 | 1000 | те же 5400 с другой руины |
| 3 | 6910 | 8110 | 1000 | 1000 | 1000+1000 = 2000 |

От 1→2: food +2400, wood +3000 — ровно награды второй руины.
От 2→3: food +1000, wood +1000 — ровно третья. Сервер честно прибавляет.

## 4. Почему это «безопасная» запись

- Не тратит гемы, не сносит постройки, не меняет королевство, не трогает альянс.
- Только забирает уже начисленные награды руин в склад.
- Если наград нет (типично для старой фермы вне туториала) — ожидаем `ok:1`
  с пустым `rewards` **или** ошибку без изменения ресурсов. Оба варианта
  для аккаунта безопасны; важно смотреть `user_city.resource`.

Ограничение честности: это **не** «сбор с ферм/лесопилок». Такой команды
в полном круге не было. Для бота фермы её ещё предстоит поймать отдельным
коротким сценарием («только тапнуть ресурсные здания»).

## 5. Как послать сами (`10_send_cmd.py`)

Скрипт умеет режим `--op` (собирает `call:commit`).

Проверка без сети:

```powershell
$env:PYTHONIOENCODING='utf-8'
cd E:\protocol_analysis\capture
python 10_send_cmd.py --session mitm\session_bundle.json --op Prophase:collectCityAllRewards --dry-run
```

Боевая отправка (allowlist + актуальный seq):

```powershell
python 10_send_cmd.py --session mitm\session_bundle.json --op Prophase:collectCityAllRewards --allow-write --seq 28 --out mitm\write_samples\collect_live_resp_seq28.bin
```

(`seq` можно не указывать, если в `session_bundle.json` уже есть `seq_next` — скрипт подставит.)

Правила безопасности в скрипте:

- `SAFE_WRITE_ALLOWLIST` = `{Prophase:collectCityAllRewards}` — открывается `--allow-write`.
- `DANGEROUS_BLOCKLIST` (upgrade, leaveAlliance, clearCityRuin, …) — даже с
  `--allow-write` нельзя; нужен `--force-unsafe` (на фермах не использовать).
- `args` по умолчанию: `{"type":"ruin","uid": <uid из JWT>}`.
- `fpid` берётся из JWT / `session_bundle.json`.

Сессия на момент разбора: ферма `uid=71206420`, `fpid=182070973`.
На ней в круге collect **не вызывался** — руин туториала, скорее всего, нет.
Живой тест всё равно полезен: увидим форму ответа «нечего собирать».

## 6. Результат живого теста

Время: **31 октября 2026, ~13:25 Europe/Sofia** (сессия фермы на netbot_test, uid=71206420).

| Попытка | seq | Ответ | Смысл |
|---------|-----|-------|--------|
| 1 | 1 (дефолт) | `{"ok":98,"seq":28}` | сервер отверг: неверный seq, подсказал ожидаемый **28** |
| 2 | 28 | `ok:1`, `payload.rewards: []` | принято; собирать было нечего |

Важный урок: у `call:commit` есть **счётчик `seq`** на сессию. После логина он растёт
(1, 2, 3…). Если прислать старый/чужой номер — `ok:98` и в ответе правильный next seq.
В нашем harvest последний commit был `seq=27` → слать надо `28`.
В `session_bundle.json` теперь поле `seq_next` (после успеха = 29).

Живой ответ (сокращённо):

```json
{
  "ok": 1,
  "payload": { "rewards": [] },
  "data": {
    "set": {
      "user_data": [{
        "uid": 71206420,
        "id": 48,
        "content": {
          "ruin": {
            "156000009": [], "156000010": [], "156000011": [],
            "156000012": [], "156000013": [], "156000014": [],
            "156000015": [], "156000017": [], "156000018": [],
            "156000019": [], "156000020": []
          },
          "battle": { "155600006": [], "...": [] },
          "first_build_hospital": 1
        }
      }]
    }
  }
}
```

- Наград нет (`rewards: []`) — у старой фермы руины туториала давно собраны.
- Блока `user_city.resource` в ответе **нет** (нечего прибавлять) — склад не менялся.
- Сырой файл: `mitm/write_samples/collect_live_resp_seq28.bin` (+ `.json`).

Вывод: команда и обёртка верные; на ферме это no-op. Чтобы увидеть рост food/wood
как в образцах 1247/1459/1559, нужен аккаунт с несобранными руинами (новый замок)
или сначала поймать обычный сбор с построек.

## 7. Следующий безопасный кандидат

1. **Поймать обычный сбор с построек** — короткий MITM: зайти на тестовый замок,
   тапнуть ферму/лесопилку/шахту/дом серебра, остановить запись, найти новый `op`.
2. Пока этого нет, следующий относительно мягкий write из каталога —
   не брать: `City:upgradeObject` тратит ресурсы; `Item:useConsumableItem` жжёт предметы;
   `clearCityRuin` меняет карту. Лучше сначала добрать «настоящий collect».
