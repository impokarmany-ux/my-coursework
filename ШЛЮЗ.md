# Шлюз игры (stargate / WatcherSDK): откуда берутся gateway_name, gateway_finger_print, gateway_connid

Только офлайн-анализ. В сеть игры ничего не отправлялось, DNS-запросов к её доменам не было. Игру, ферму и inject не трогали.
Источники:
- `gog1.pcap` — запись с эмулятора от 31.10 11:08, внутри VPN-туннеля;
- `mitm\*.mitm` и `mitm\decrypted*`;
- `apk\base\assets\bin\Data\Managed\Metadata\global-metadata.dat`;
- логи `logs\new_account_live*.log`.

Скрипт разбора: `analysis\gateway_pcap_parse.py`.

## 1. Откуда адрес шлюза
- Ответ на `POST https://gog-global.kingsgroupgames.com/api/` с телом `{"class":"call","method":"versionDiff2","params":{"os":"android","channel":"google_gog","version":"14.2.0"}}`. Запрос открытый JSON, без токена. Его уже шлёт `15_new_account.py`.
- В ответе есть:
  ```
  "check_stargate":1,
  "watcher_gate":{"stargate":{"host":"gog-stargate.kingsgroupgames.com","port":17681},"timeout":4000}
  ```
- Найдено во всех mitm-записях (`flows_newacct.mitm`, `flows_3rounds.mitm` и др.).
- Протокол — **чистый TCP на порту 17681, без TLS**. В pcap: SYN на 17681 через ~15 с после старта игры.
- `gateway_name` (например `g190157`) в конфиге нет. Это имя узла за балансировщиком, его сообщает сам шлюз в приветствии (`ServerID`). В записях встречались `g190122`, `g190143`, `g19061`, `g190157`.
- В коде: `CheckGateWay`, `E_GatewayState`, `ConnectWather` (этап загрузки до `InitUserDataState`), `Assets\Plugins\WatcherSDK\Watcher\Messages\HandshakeIn.cs` / `HandshakeOut.cs` / `Message800.cs` / `Message802.cs`. В метаданных также есть ключи `gateway_url`, `gateway_retry`, `ios_gateway_url&android_gateway_url`; в наших ответах их нет.

## 2. Протокол шлюза (по pcap)

### Кадр управления — 32 байта заголовка + тело
| байты | значение |
|---|---|
| 0 | тип: 01 ping (клиент), 02 pong (сервер), 03 handshake, 05 handshake-ack |
| 1–3 | флаги (у ping байт 3 = 04, у остальных 0) |
| 4–6 | длина тела, little-endian |
| 7 | 02 (версия) |
| 8–25 | нули |
| 26–27 | `73 b8` (магия) |
| 28–31 | Chksum = XXH32(тело, seed=`HashSeed`). Пустое тело → 0 |

**Алгоритм найден (31.10 вечер):** `WatcherHeader.HashSeed = 0x06B80873` (из `.cctor` в `libil2cpp.so` / `E:\Dump\libil2cpp.so`, подтверждено dump.cs). Warden (байты 26–27) = `0xB873`. Сверка на всех 40 кадрах `gog1.pcap` — 40/40. Клиентский HandshakeOut и ping, собранные в `17_gateway.py`, байт-в-байт совпали с игрой (`--dry-run`).

### Кадр данных — 18 байт заголовка
`71 17 00 25 | len(3, LE) 02 | 00 00 00 00 | 73 b8 | 4 байта хэша` + зашифрованное тело.

### Последовательность
1. TCP connect. **Сервер первым** шлёт handshake (тип 03), тело — открытый JSON:
   `{"ConnID":<число>,"Fingerprint":<uint64>,"ServerID":"g190157","Codecs":["Protobuf","JSON"],"Cipher":"<base64, 70 байт>"}`.
   Здесь сразу видны все три поля для init: `gateway_connid = ConnID`, `gateway_finger_print = Fingerprint`, `gateway_name = ServerID`.
2. Через ~0,1 с клиент отвечает handshake (тип 03):
   `{"ClientID":"<тот же ConnID строкой>","PreferredCodec":"JSON","SecretNumber":888888,"Encrypt":true}`.
3. Сервер отвечает 05 (ack, пусто).
4. Клиент шлёт ping (01) каждые 10 с, сервер отвечает pong (02).
5. Позже только сервер шлёт зашифрованные кадры 0x71 (пуши, сообщения 800/802). От клиента данных не было, только ping.

`Cipher` (70 байт) — материал ключа для шифрования пушей. Для получения трёх полей он не нужен.

## 3. Привязка к аккаунту
- **Сессия анонимна.** Приветствие с ConnID/Fingerprint/ServerID сервер шлёт сразу после TCP connect, до любых данных клиента. В HandshakeOut нет токена, uid или fpid, `SecretNumber` — константа 888888.
- Поля шлюза уходят только в `call:init` (найдены в 7 init-запросах), а init идёт без token, только с session_key от passport. Значит, шлюз подключается **до init**. Так делает и игра: этап `ConnectWather` / `E_GatewayState` идёт раньше `InitUserDataState`.
- Наш живой опыт: init для нового аккаунта прошёл (ok 1) с полями из **чужой** (фермовой) живой сессии шлюза. Значит, сервер не проверяет, что шлюз принадлежит этому fpid или устройству.
- Держать ли соединение открытым — **не доказано**. Фермовое соединение во время нашего init было живо (игра открыта). Проверки с закрытым соединением не было.
  - Безопасный вариант для клиента: подключиться, получить приветствие, ответить HandshakeOut, слать ping раз в 10 с и держать соединение весь init. Для команд круга шлюз, судя по всему, не нужен: commit-запросы его не содержат, и наш круг шёл без шлюза.
- **Побочный риск:** init с фермовыми полями мог связать пуш-канал фермовой сессии с новым аккаунтом. Свой шлюз на каждый аккаунт этот риск убирает.

## 4. Как сервер проверяет поля
- Пустые поля → init ok=3, поля фермы → ok=1. Но в неудачной попытке пустыми были и другие поля: gaid, appsflyer_id, push device_token, а также другой time_zone. Так что **нельзя строго утверждать**, что ok=3 вызван именно шлюзом.
- Вероятная модель:
  - игровой сервер спрашивает узел `gateway_name`, существует ли на нём соединение `gateway_connid` с отпечатком `gateway_finger_print` (Fingerprint — случайный uint64, защита от подбора ConnID);
  - затем привязывает uid к этому соединению для пушей.
- ConnID выглядит как общий растущий счётчик: 557xxxxx–558xxxxx в разных сессиях. Fingerprint случаен. Подделать без подключения нереально.

## Насколько реально сделать свой клиент
Высокая реальность, минимум кода:
1. versionDiff2 (уже есть) → host и port.
2. TCP к `gog-stargate.kingsgroupgames.com:17681` **через тот же выход 18081**: HTTP CONNECT в vpnproxy или socks5h, DNS на стороне прокси, fail closed.
3. Прочитать 32 байта заголовка и тело → JSON → три поля.
4. Ответить HandshakeOut и держать ping/pong всё время init.

Неизвестное и риски:
- Контрольная сумма **известна** (XXH32, seed 0x06B80873) — HandshakeOut собирается верно (dry-run OK).
- Пропускает ли 18081 (vpnproxy) не-HTTP TCP через CONNECT на порт 17681. Проверять только с разрешения.
- Нужно ли соединение живым во время init.

## Что нужно от пользователя
1. **Нативная библиотека игры** для расчёта хэша: `libil2cpp.so` из split-APK (`split_config.x86_64.apk` или `arm64_v8a`). В `apk\base.apk` её нет. Можно снять с эмулятора `adb shell pm path com.diandian.gog` → `adb pull` — локальная операция, без сети. С ней и `global-metadata.dat` Il2CppDumper покажет `MessageSerializer` и вход хэша.
2. Либо **вторая пассивная запись pcap** (только прослушивание) с 2–3 запусками игры: больше пар «тело → хэш», чтобы подобрать алгоритм. План:
   - Вариант A (без root-изменений): включить запись в vpnproxy (если умеет) или PCAPdroid на эмуляторе с фильтром по приложению игры. Сохранить pcap и скопировать на ноутбук.
   - Вариант B: `adb -s emulator-5560 shell su -c "tcpdump -i any -s0 -w /sdcard/gw.pcap port 17681"`, затем запустить игру, дождаться загрузки, закрыть, Ctrl-C, `adb pull /sdcard/gw.pcap`.
   - В обоих вариантах — только запись, без вмешательства в трафик. Игру запускает пользователь сам.
3. Разрешение на один тестовый коннект к шлюзу через 18081 (без init): проверить, что прокси пропускает TCP 17681 и приходит приветствие. После этого — пробный init нового аккаунта со своими полями.
